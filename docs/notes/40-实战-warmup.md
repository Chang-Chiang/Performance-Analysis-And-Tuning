# 40 · 实战 · `warmup`（算法级 O(N) → O(1)）· **开篇**

> **TMA 分类**：Misc / **算法层**（本系列最纯粹的"最高杠杆"演示）· **加速比**：**109x 本机** / 70x 文档
>
> 🎯 **整个 16 实验系列的开篇最强佐证**：从 O(N) 循环换成 O(1) 数学公式，比任何 SIMD/布局/预取都狠得多。

---

## 一、读题（Step 0）

**任务**：`sum = Σ i for i in 1..N`（N=1000，bench.cpp 里 constexpr）。

**基线**（O(N)）：
```cpp
int sum = 0;
for (int i = 1; i <= N; ++i) sum += i;
return sum;
```

**优化**（O(1)，数学闭合式）：
```cpp
return (N * (N + 1)) / 2;   // 高斯求和公式, 一步到位
```

## 二、本机实测

```
基线 O(N): bench1 = 36.0 ns   (19,416,836 iterations)
优化 O(1): bench1 = 0.331 ns  (2,116,326,473 iterations)
加速比 = 36.0 / 0.331 = 109x
```

**加速比比工程文档 70x 更高**——原因见 §三。

## 三、🎯 深度拆解：**为什么是 109x 而不是 1000x**？

**理论直觉**：N=1000，把 1000 次加法变成 1 次乘法+移位 → 应该 **~1000x 加速**。**为什么只有 109x**？

### 原因 1：**编译器已经把基线"偷偷"向量化了**

- N=1000 是 `constexpr` → 编译器看到整个循环
- `-O3 -march=native` 把 `for (i) sum += i` 变成 **AVX2 SIMD 归约**（8 lanes at once）
- 1000 次加法 → 125 次向量加法 → 3-4 层 log-tree 归约
- **基线不再是 O(N) 标量，是 O(N/8) SIMD** → 36 ns ≈ 125 cycles ✓

### 原因 2：**优化版被折叠成编译期常量**

- `(N * (N+1)) / 2` 中 N 是 constexpr = 1000 → 编译期算出 **500500**
- 整个 `solution()` 被优化成 `mov eax, 500500; ret`
- 0.331 ns ≈ 1 cycle = 一个 `mov` ✓

### 净结果

**基线** ≈ 125 cycles（SIMD 归约）
**优化** ≈ 1 cycle（编译期常量 + 一条 mov）
**比值 = 125x**，实测 109x（有函数调用/循环 setup 开销摊薄）

> 💡 **这就是"如果只有算法能赢，其他优化只能追平"**：编译器可以 SIMD 加速 O(N)，但**永远无法把 O(N) 变成 O(1)**——因为数学闭合式必须由人告诉它。**算法是编译器的天花板之外**。

## 五、"warmup" 这个名字的隐喻

工程原实验叫 `warmup` 是因为性能基准里有个概念叫 **"warm-up iterations"**——先跑几轮预热让 cache/分支预测稳定。**但真正的"预热"是把 O(N) 的"每次都要重算"变成"一次算好、O(1) 查询"**——**用空间换时间**的极致：
- 预计算 `sum[i]` 存到 `prefix[i]` → 后续任意区间查询都是 `prefix[r] - prefix[l-1]` 一次减法
- 或本实验这样：**用数学公式把"过程"折叠成"结果"**

这在真实系统里比比皆是：
- **数据库索引 / 物化视图** = 用空间换查询时间
- **CDN 缓存 / Redis** = 用副本换远程访问
- **哈希表 vs 有序数组二分** = O(1) vs O(log n)
- **FFT 换 DFT** = O(N log N) 换 O(N²)

**warmup 是本系列 5 号实验（`basis/Algorithm/max_sum.cpp` O(n³)→O(n)）的最纯粹"回归"——都是"用算法层杠杆一举掀翻一切"**。
