# 54 · 实战 · `lto`（Link-Time Optimization 跨翻译单元内联）

> **TMA 分类**：Misc / 编译器层 · **加速比**：**1.51x 本机** ≈ 1.50x 文档

---

## 一、读题

**任务**：Ambient Occlusion 光线追踪渲染（AO 项目，多个 `.cpp` 文件：`ao.cpp` / `ao_intersect.cpp` / `ao_render.cpp` / `ao_occlusion.cpp` 等）。

**普通编译**：每个 `.cpp` 独立编成 `.o` → 链接器只能拼机器码 → **跨文件的函数看不到 IR，无法内联/常量传播/死代码消除**。

**LTO**（`-flto`）：编译时保留 **LLVM IR 位码**到 `.o` → **链接阶段**把所有模块 IR 合并 → 编译器获得**全局视野** → 跨 TU 内联、常量传播、DCE。

## 二、本机实测（工程提供 build_nolto/ 与 build/ 两套）

```
build_nolto/ (无 LTO): bench1 = 533 ms  ← 基线
build/          (LTO): bench1 = 352 ms  ← 优化
加速比 = 533 / 352 = 1.51x  ✅  工程文档 1.50x
```

## 三、为什么 LTO 能赚 1.5x？

AO 项目**跨 6+ 个 `.cpp` 文件**：小工具函数（`Vector` 运算、`OrthoBasis` 构造）分散在不同 TU。开 LTO 后：
1. **跨文件内联**：`intersect` 里调用的 `ray::at(t)` 等小函数被内联 → 消 CALL 开销（对照 52 号）
2. **常量传播穿透**：某个编译时常量跨文件传播，触发分支消除
3. **全局 DCE**：链接时看到"这个函数其实没人调"→ 整个删掉
4. **寄存器分配更优**：函数边界少了 → 参数拷贝少了

## 四、`-flto=thin` vs `-flto=full`

| 模式 | 特点 | 何时用 |
|------|------|-------|
| `-flto=full` | 全 IR 合并统一优化 | 极致性能；小项目 |
| `-flto=thin` | 模块独立按需导入，**并行编译** | **大工程默认**（比 full 链接快得多，收益接近） |

**现代实践**：日常用 `-flto=thin` + `-fuse-ld=lld`（LLD 才能正确处理 ThinLTO）。

## 五、副作用与注意

- **编译时间↑**（尤其 full）：链接阶段做全项目 IR 优化
- **二进制可能变大**（更多内联）→ **可能触发 frontend bound**（I-Cache/iTLB 压力）
- **调试信息可能错乱**：跨 TU 内联后 gdb 单步会"跳"
- **对静态库 `.a` 无效**：`.a` 是最终码，需要重编

## 六、一句话收口

> **LTO = 让编译器在链接阶段"再看一遍所有代码"**——1.51x 加速本质是"**跨文件把该内联的内联、该删的删**"。工程上：**中大项目开 `-flto=thin` 是几乎免费的午餐**（编译时间小涨、运行时间明显下降）。**但它救不了运行时函数指针**（qsort 那种，见 52 号）。
