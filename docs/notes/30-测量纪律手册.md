# 30 · 测量纪律手册（元教训与陷阱清单）

> **立意**：八步实战跳出来的**通用教训**，与具体优化手法无关，但**决定了你所有加速比数字是否可信**。性能工程师最重要的本能不是"知道多少优化"，而是"**知道什么时候该怀疑自己的数据**"。

---

## 一、四条贯穿全篇的元教训

### 🥇 元教训 1：**反直觉结果先怀疑测量，别急着怀疑计算机**
> 出处：**实验 ⑥ 伪共享第一次跑出"反了"的数字**（伪共享 0.000576s 反而比串行快）。

微基准第一次跑出**违反理论**的结果，**99% 是测量误差**而不是物理规律被推翻。诊断三步：
1. **规模太小**？测的信号被噪声淹没 → 放大问题规模
2. **只跑了一次**？单次抖动就能翻转排序 → 多次取平均
3. **没绑核**？OS 调度把线程搬来搬去 → `OMP_PROC_BIND`/`taskset`

**修完方法再测**，方向一般就正过来了。这一条是**所有测量事故的第一性原则**。

### 🥈 元教训 2：**"已优化 ≠ 快"，多角度必须交叉验证**
> 出处：**实验 ⑧ AoS `-Rpass` 说"vectorized"，但实测仍慢 5x**。

单一工具的"良好报告"只覆盖**一个视角**：
- `-Rpass` 报 **Core** 视角（有没有用 SIMD），报不了**Memory**（带宽多糟）
- `perf stat` 报**硬件计数器**（IPC/miss），报不了**算法**（是不是复杂度撞墙）
- 加速比报**总时间**，报不了**是否命中瓶颈根因**

**规矩**：任何"已优化"结论至少 **两个独立证据**（如 `-Rpass` + 计时；`perf stat` + TMA 一级；加速比 + CPU 利用率）。

**IPC 本身也会骗人**（**实验 41 坐实**）：`loop_interchange_1` 开 SIMD 后，原始 IPC 反而从 4.23 降到 2.73——因 SIMD 指令每条多周期退休但干 8 倍活。**判优前看指令总数 + 是否向量**，不要拿 IPC 单指标下结论。

### 🥉 元教训 3：**加速比强依赖硬件与负载，换机器就要重测**
> 出处：**实验 ② 链表 vs 数组：文档"400 倍"，本机跑出 1.8 万倍**；**实验 ⑥ 文档 `false_sharing_1` 15.8x，本机测得 1.2-1.5x**。

同一个"优化前后对比"在不同机器/输入下能差**几个数量级**：
- 缓存行大小 / L3 容量 / 内存带宽 / NUMA 结构
- 单路 vs 多插槽（**伪共享在多插槽上会灾难性地慢**）
- 输入分布（最坏 vs 平均）
- 是否有其他进程干扰

**规矩**：**报告加速比必须同时记录机器配置、编译命令、输入规模、绑核策略**。"某实验 6.9x" 这种孤零零的数字没有意义。

### 🏅 元教训 4：**基线一旦被污染，优化就是玄学**
> 出处：**实战 ③ rdtsc.c 里 `k` 是未初始化局部变量** → 起点是垃圾 → 平均被污染。

真实工程里 90% 的"优化没效果 / 效果虚高"栽在测量不严谨：
- **变量未初始化**（像 `k`）
- **只测第一次**（冷启动包含缺页/分支预测学习，虚高）
- **没预热 cache**（工作集还没进 L1/L2）
- **动态调频**（CPU 频率飘忽）
- **有后台任务**（其他进程抢资源）

## 二、基线七条纪律（每次测前 checklist）

| # | 纪律 | 命令/做法 |
|---|------|----------|
| 1 | **编译要和生产一致** | `-O2` 或 `-O3`（`-O0` 分析瓶颈是假的）；加 `-g` 让工具能定位源码行 |
| 2 | **锁 CPU 频率** | `sudo cpupower frequency-set --governor performance` |
| 3 | **绑核运行** | `taskset -c 0 ./bench`；OpenMP 用 `OMP_PROC_BIND=spread OMP_PLACES=cores` |
| 4 | **关干扰源** | 关掉浏览器/后台同步/其他 perf；单用户环境 |
| 5 | **预热 + 多次取平均** | 先跑一遍丢弃（cache 冷、缺页、分支预测学习），再跑 N 次取 min/median |
| 6 | **变量初始化** | 所有计时/累加变量显式 `= 0`（`k` 的教训）|
| 7 | **记录环境** | 记下 CPU 型号/核数、编译器版本、内存、输入规模、绑核策略——**加速比要可复现** |

## 三、常见"数据不可信"陷阱（八步实战都踩过）

### 陷阱 1：亚毫秒测量被 fork-join 淹没（**实验 ⑥**）
- 症状：程序 <1ms 就结束 → OpenMP 启动线程开销 100μs 级 → **噪声 > 信号**
- 解法：**放大规模**（问题 × 10~100）、增加迭代次数取平均、或换 CPU 周期计数（`rdtsc`）

### 陷阱 2：单次运行抖动翻转排序（**实验 ⑥ 第一次**）
- 症状：理论 A>B，实测 B<A → 极可能是单次抖动
- 解法：**至少跑 5~10 次，看 min 或 median，检查排序稳定性**

### 陷阱 3：`chrono`/`gettimeofday` 分辨率不够
- 症状：Kadane O(n) n=1000 显示 0μs（**实验 ① 彩蛋**）
- 解法：用 `rdtsc` 数周期、或放大规模、或用 `perf stat`

### 陷阱 4：DCE 死代码消除把基准优化没了
- 症状：`for(...) sum+=a[i]` 编译后 sum 没被打印 → **整段循环被删**
- 解法：**volatile 累加器 + 最后 printf**；或 `-fno-tree-vectorize` 观察差异

### 陷阱 5：内存首触污染 sys 时间（**实验 ③**）
- 症状：大数组第一次访问 sys 时间高（页故障）
- 解法：**预热跑一遍再测**；或用 `first-touch` 策略在并行区初始化（**07 § 四 / 08 § 四**）

### 陷阱 6：混合架构 perf 数字被拆两份（**实验 ⑤**）
- 症状：`perf stat` 输出 `cpu_atom/...` + `cpu_core/...` 两组
- 解法：**看时间占比最高的那组**（本机大核 98%/83% → 用 `cpu_core`）；或用 `taskset` 强制绑到大核

### 陷阱 7：`-Rpass` 只报 Core 不报 Memory（**实验 ⑧**）
- 症状：报告说"vectorized"但实测仍慢
- 解法：**`-Rpass` + `perf stat` 双视角**（Core + Memory）；见元教训 2

### 陷阱 8：`num_threads(T)` 硬编码挡住扫线程（**实验 ⑦**）
- 症状：`OMP_NUM_THREADS` 环境变量被代码里的 `num_threads(4)` 覆盖
- 解法：扫线程数时改用 `omp_set_num_threads(T)`，或去掉硬编码

### 陷阱 9：`MPI_Send` 小消息内部缓冲，测不到启动延迟 α（**实验 ⑩**）
- 症状：想量“合并小消息”优势，但小消息发送立即返回 → 时间看上去差不多
- 解法：**测 α 一定用 `MPI_Ssend`（同步发送）**，它会真等到对方 Receive；或配对 MPI_Recv 时不提前缓冲

### 陷阱 10：MPI 集合通信两大“直接挂”陷阱（**实验 ⑩**）
- **`MPI_Gather` sendbuf 与 recvbuf 不能重叠**（同一 C 数组会 "Buffers must not be aliased" 直接 Abort）→ 用独立局部缓冲 `Cl`
- **`MPI_Reduce` 是集合通信，所有 rank 必须一起调**——只在 rank0 里调 → **死锁**（非零 rank 永远等不到）。要么全部 rank 都调，要么直接 rank0 自己 printf

### 陷阱 11：Intel MPI 在容器/sandbox 里 `mpirun` 起不来（**实验 ⑩环境**）
- 症状：`hydra_bstrap_proxy` 无法孵化，提示 firewall / localhost bootstrap cannot launch
- 解法：**绕开 mpirun，直接用 `mpiexec.hydra -bootstrap ssh -n N ./app`**（需 ssh localhost 免密）；或容器内预配 sshd

### 陷阱 12：CUDA 12+/13+ 删了一些 `cudaDeviceProp` 字段（**实验 ⑨环境**）
- 症状：`p.clockRate`、`p.l1CacheSize` 编译失败
- 解法：改用 `p.major`/`p.minor`/`p.multiProcessorCount`/`p.warpSize`；频率用 `cudaDeviceGetAttribute` 新 API

### 陷阱 13：“教科书加速比”在新硬件上会直接失效（**实验 ⑨b · ⑩b 同时踩到**）
- 症状：
  - 工程文档写“交错配对消 warp 分化快 1.7x (RTX 3090)”，本 Blackwell RTX 5070 Ti 上实测**交错反而慢 9%**
  - 理论写“Scatter 比 Bcast 少传 P 倍字节”，单机 loopback 实测**二者时间差不超 2%**
- 根因：**两种经典结论都有默认前提**——
  - warp 分化的代价随 GPU 代际大幅下降，交错反而可能引入 bank conflict
  - 减通信量的优化**只在通信真的是瓶颈时才有收益**；单机 loopback 上计算淹没一切
- 解法：**换硬件 / 换网络 → 重新测**；先看瓶颈在不在那里（`perf stat` / `MPIP` / `ncu`），**先分诊再开药**——而不是背历史数字直接上药。

> 这一项本质上是 **元教训 3** 的具体实例：加速比强依赖硬件与负载。⑨b/⑩b 两个“失败实验”比任何成功实验都更值得反复看——它们拆穿了“优化手法”的“默认适用前提”。

## 五、从"怀疑"到"证据"：三层交叉验证金字塔

```
第三层 (根因):   TMA / -Rpass / IPC / cache-miss  (硬件计数器与编译器视角)
   ▲
第二层 (信号):   多次运行, min/median, 绑核, 预热   (统计意义)
   ▲
第一层 (基线):   固定编译选项 + 输入 + 环境         (可复现性)
```

**规矩**：加速比数字必须**同时**满足三层——**可复现 + 有统计显著 + 能对应到硬件根因**——才算"证据"，否则只是"猜测"。

## 六、一句话收口

> **性能优化里最贵的错误不是"没优化"，是"优化了但数字不可信"**。
> **反直觉先怀疑测量；单一视角必骗人；换机器就要重测；基线七条纪律每次跑前 checklist**。
> 这份手册的每条教训都来自八步实战里**踩过的坑**——把它们内化成本能，你的加速比数字才配放进汇报。
