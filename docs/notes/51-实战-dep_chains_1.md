# 51 · 实战 · `dep_chains_1`（M 路并行破链表依赖）

> **TMA 一级**：Core_Bound（**Pointer Chasing / 依赖链**）· **优化技术**：**M 路 l1 元素共享一次 l2 遍历**·**加速比**：**3.49x 本机** ≈ 3.6x 文档
>
> 💡 **本实验的独特价值**：**链表 = 依赖链的物理极限**（每个 `next` 都必须等前一个）。M=4 手法本质是"**把 1 条依赖链拆成 1 条链 + 4 个独立工作**"——即 21 号母题 ① "掩盖延迟" 在 CPU 单核上的化身。

---

## 一、读题（Step 0）

**任务**：l1、l2 各 10000 个节点的随机链表，找 l1 里每个值 v 是否在 l2 出现，若出现则累加 `getSumOfDigits(v)`。

**基线**（M=1，最直白）：
```cpp
for each node in l1:                    // 10000 次
  l2 = head2
  while l2:                              // 最坏 10000 次
    if l2->value == v: hit; break
    l2 = l2->next                        // ← 每步依赖上一次结果
```
→ **N × N = 1 亿次 pointer chase**，每次等前一个 next 才能读 value。

**优化**（M=4）：
```cpp
for each GROUP of 4 nodes in l1:         // 2500 组
  vals[4] = {l1->value, l1=l1->next, ...}   // 一次性取 4 个 l1 值 (4 次链)
  l2 = head2; found = 0
  while l2:                                // 一条 l2 链, 服务 4 个查找
    for j in 0..3:
      if l2->value == vals[j]: hit for vals[j]
    if all found: break
    l2 = l2->next                          // 仍依赖链, 但 4 次比较共享
```
→ **N/4 × N = 2500 万** 次 l2 遍历，且**每次 while 循环里有 4 个独立 compare**（第 6 课"消依赖"的 M 路版本）。

**基线切换只要一行**：`sed 's/solutionM<4>/solutionM<1>/'`（模板参数从 4 改回 1）。

## 二、Step ①②③④ 本机实测

| | 基线 M=1 | 优化 M=4 | 变化 |
|--|---------|---------|------|
| **Google Bench** | **59.7 ms** | **17.1 ms** | **3.49x** ✅ |
| 每 iter cycles | 359 M | 117 M | ↓ 3.07x |
| 每 iter instructions | 531 M | **769 M** | **↑ 1.45x** |
| **IPC** | **1.48** | **6.56** | **↑ 4.4x** 🔥 |
| cache-miss / iter | 8.2 K | 2.2 K | ↓ 3.7x |

---

## 三、🎯 加速机制：**依赖链拆散 = 流水线填满**

**基线 IPC 1.48** = 大核峰值 4-6 只用 25%——**因为 CPU 每周期只能推进一个 l2->next 加载**。链表节点在堆上分散，每次 `l2->next` 都触发 L1/L2 miss（cache-miss 8K/iter 也说明）。CPU 流水线大部分时间在**等这条依赖链**。

**优化 IPC 6.56** = **已经打满**大核发射宽度。为什么？
- 4 个 compare 互不依赖（`l2->value == vals[j]` for j=0..3）→ 流水线**并行发射 4 个**
- l2->next 依赖链的**等待时间**被这 4 个独立工作**填满**了
- 每 iter instructions ↑ 1.45x（多了 4-1=3 次比较）但 cycles ↓ 3x

**净收益 = 3.49x**，正好接近"1/4 依赖 + 3/4 独立工作"的直观预期。

> 💡 **这就是第 6 课"消依赖暴露 ILP"在真实数据结构上的最经典案例**：
> - 依赖链本身没法消除（链表 `next` 就是硬依赖）
> - 但可以**在依赖链上叠加独立工作**，让流水线等 next 的时候顺手做别的
> - 这和 CUDA 双缓冲、MPI 非阻塞重叠、`swmem_prefetch_1` 预取 —— **同一思想的不同硬件化身**（21 号复盘"母题 ① 掩盖延迟"）

## 四、和 48 号 vectorization_2 的关系（**消依赖谱系**）

| | **48 vectorization_2** | **51 dep_chains_1** |
|--|----------------------|-------------------|
| 依赖类型 | **循环累加器依赖**（`acc = acc + carry`） | **指针追逐依赖**（`l2 = l2->next`）|
| 消依赖思路 | **拓宽累加器让 carry 移出循环** | **保留依赖链但用 M 路并行填充等待时间** |
| 效果 | 从"完全串行"→ "SIMD 完全并行" → 21x | 从"1 条链 IPC 1.48" → "1 条链+4 compare IPC 6.56" → 3.5x |
| 关键不同 | 依赖**被消除** | 依赖**仍在**、只是被**藏** |

**"消依赖"和"藏依赖"是两味不同的药**——消能消就消（收益大），消不掉就藏（本实验，收益小但仍有）。

## 五、M 大小的选择（可扩展探索）

M=4 是本实验的默认，为什么不是 8/16？
- **M 越大**：每 while 循环做更多独立 compare → IPC 越接近峰值
- **上限**：SIMD 16 lane 或流水线并行度 4-6 → M 超过 8 收益饱和
- **代价**：M 越大，`std::array<unsigned, M> vals` 栈上占用 + 每 while 内多 M 个比较 → 一旦大部分 val 都找到了，多比较就成浪费（`if (++found == M) break`）
- 实际中 M=4~8 常是甜蜜点

## 七、一句话收口

> **链表 = 依赖链的物理极限**——每次 `l2->next` 都得等。M=4 手法不"消"依赖（做不到），而是"**让等待时间被 4 个独立比较填满**"——从 **IPC 1.48 拉到 6.56**，3.5x 加速。这是"**消不了就藏**"哲学最生动的标本，也和 CUDA 双缓冲、MPI 非阻塞重叠、48 号拓宽累加器构成完整的"**依赖链管理**谱系"。
